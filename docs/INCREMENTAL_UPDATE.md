# Инкрементальный сбор каждые пять минут

Статус: подготовлено в ветке `codex/incremental-five-minute`. **Не включено в production**, реальные API-выгрузки и Actions не запускались. Требуется подтверждение владельца перед слиянием в main.

## Архитектура

- Сохраняется полный совместимый основной JSON, форумный справочник, история и metadata. База следующего runner — последний согласованный Git-коммит main, а не cache/artifact или временные файлы.
- `/full` возвращает актуальный состав по UUID. Сравниваются scoredCount и сумма имеющихся подробных оценок с score. Новые UUID и изменения получают отдельный `/scores`; остальные подробности используются как есть. Нулевой score=null у участника без оценок не вызывает ложного изменения.
- Затем `/live` проверяет весь состав, количество и сумму. Изменившиеся карточки перечитываются, максимум три проверки согласованности. Если после третьей проверки состав/оценки продолжают расходиться, публикации нет. Правила раунда должны оставаться 5 оценок, шкала 1–5 и проход 15.
- Массив изменившейся карточки заменяется целиком, не дополняется: удаление оценки и исправление суммы при прежнем количестве учитываются. Исчезнувшие UUID остаются в archivedMembers с исходными оценками. CSV остаётся независимым авторским справочником.
- `fetchedAt` обновляется только для реально прочитанных подробных карточек. `exportedAt`/lastSuccessfulAt — время успешной сверки полного состояния по публичным сводкам, не обещание новой проверки каждого комментария.
- После валидации обновляются история before/after, даты и состав выборки. Файлы сначала готовятся в .staging. Только полностью успешный job может одним Git-коммитом сохранить четыре файла и опубликовать Pages. Замена локальных файлов по rename не является общей файловой транзакцией; неуспешный runner отбрасывается, а production и Git остаются на последней полной версии.

## Расписание и конфликты

```yaml
schedule:
  - cron: '*/5 * * * *'
    timezone: 'Europe/Moscow'
workflow_dispatch:
  inputs:
    mode:
      type: choice
      options: [auto, incremental, full]
      default: auto
concurrency:
  group: ib19-publish
  cancel-in-progress: false
```

Эта же группа уже используется deploy.yml. Активный сбор/публикация не прерывается новым tick. GitHub может заменить ожидающий tick более свежим, поэтому это не очередь всех 288 событий: для снимков важно последнее состояние. Checkout main выполняется после приобретения блокировки, с полным Git для восстановления. Запуск на любой другой ветке защищён job-условием и не публикует сайт.

Freshness gate использует **реальное время выполнения**, пропускает лишний scheduled run, если в текущем пятиминутном интервале уже была успешная выгрузка. Manual run не подавляется. Задержка/пропуск Actions не приводит к чтению старого запланированного SHA. При конкурентном push человека обычный git push отклоняется; force-push и автоматического слияния данных нет, deployment не выполняется.

Пять минут — минимальный поддерживаемый интервал GitHub Actions, но не SLA фактического выполнения. Источники: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax и https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency .

## Ограничение нагрузки

Общая очередь старта запросов: не чаще одного в 1000 мс, не более двух запросов в работе. При 429 учитывается Retry-After в секундах или HTTP-date. Cooldown общий для workers; увеличивающийся backoff 2/4/8 с, максимум три повтора. Временные 5xx/408/сетевая ошибка обрабатываются ограниченными повторами, постоянные 4xx не повторяются. Большой Retry-After не сокращается ради публикации: при исчерпании бюджета сбор прекращается.

Бюджет инкремента — 12 минут, полного — 55 минут; timeout workflow — 65 минут с запасом на тесты и Pages. При большом всплеске оценок запуск может быть дольше пяти минут: другие сборщики не стартуют одновременно. При провале промежуточная работа не записывается как действующий снимок. Возобновляемого частичного checkpoint нет: это сознательный выбор ради простоты/целостности. Повторный run проверяет последнюю успешную базу.

600 из X-RateLimit-Limit не используется как гарантированный бюджет.

## Полная сверка и восстановление

Режим `auto` выполняет полную сверку, когда со времени последнего полного успешного сбора прошло семь суток. Проверка выполняется в той же общей блокировке и с тем же ограничением темпа. Нужна для изменений комментариев и компенсирующих правок при неизменных агрегатах. Отдельной постоянной контрольной перечитки нет, согласно текущему ТЗ.

Первый запуск на старой версии metadata принимает lastSuccessfulAt как дату последнего полного сбора (до этой миграции все сборы были полными); следующие инкременты сохраняют этот исходный lastFullAuditAt. Ручной `full` запускает такую же полную сверку, ручной `incremental` позволяет временно избежать полной сверки при проблемах API. Расхождения сохраняются в существующей истории ревизий, ошибки — в Actions diagnostic artifact.

При отсутствующем/повреждённом наборе проверяются до 20 последних Git-ревизий data: используется только согласованная четвёрка файлов из одного коммита. Требуются валидные оценки, UUID, времена и совпадающие экспортные даты/последний снимок history. Восстановленная ревизия явно записывается в отчёт. Если подходящей базы нет, отказ **до API-запросов**: необходимо восстановить проверенный набор из Git. Слепой полный bootstrap с потерей авторских полей/истории не выполняется.

## Логи

collection-report.json, Actions console/summary и artifact с хранением семь дней: режим, участники, участники с новыми оценками, изменившиеся/обновлённые карточки, HTTP-запросы включая retry, 429, retry, длительность, оценки до/после, baseline полного сбора и процент экономии. Сборщик отмечает публикацию как ожидающую; финальный workflow-шаг записывает реальный outcome Pages и job. Сбой сбора не обозначается успехом.

Полные browser checks выполняются на полных сверках, unit/data checks — на каждом сборе. Build и проверки выполняются **до** коммита и push. Push через GITHUB_TOKEN не запускает deploy.yml, поэтому update-data.yml сам публикует проверенный dist.

## Экономия и время — оценки, не измерение live

На текущем локальном снимке: 3281 участник, 8320 оценок, 2887 непустых карточек. Старый алгоритм: минимум **2889** запросов на сбор, **69 336/сутки** при 24 полных сборах, без retry/догоняющих карточек.

| Изменённых карточек C за запуск | Запросы инкремента, минимум | Время самого API-сбора при 1 запросе/с, ориентир |
|---:|---:|---|
| 0 | 2 | ~1–3 с + задержки сети |
| 1 | 3 | ~2–5 с + задержки сети |
| 10 | 12 | ~11–20 с |
| 50 | 52 | ~51–70 с |
| 100 | 102 | ~101–130 с |

Не включает ожидание runner, checkout/npm/tests/build/deploy, retry, дополнительные проходы согласования. Эти накладные расходы могут занимать ещё минуты и мешать фактическому пятиминутному SLA.

В среднем за сутки при 288 ticks и одной полной сверке в неделю: `288*(2+C) + (2887-C)/7` запросов. Примеры:

- C=0: около 988/сутки, −98,6%.
- C=10: около 3867/сутки, −94,4%.
- C=50: около 15 382/сутки, −77,8%.
- C=100: около 29 775/сутки, −57,1%.

Это сценарии, не прогноз скорости выставления оценок. При непрерывных массовых изменениях число запросов/повторов может быть больше; запуски будут объединяться ожиданием блокировки. Полная сверка ожидаемо около 48 минут плюс сеть и догоняющие карточки. В это время отдельные инкременты ждут, то есть пятиминутной публикации во время полной сверки не обещаем.

## Проверки и оставшиеся риски

Локальные фикстуры покрывают: пустой инкремент, одну/несколько новых оценок, новый UUID, исчезновение UUID, удаление оценок, смену суммы, null у нулевых карточек, частичный/повреждённый API, прерывание, восстановление из Git, отсутствие базы, задержки cron, shared throttle/cooldown, 429/500/404, оба вида Retry-After, ограничение повторов/бюджета и контроль конфигурации concurrency.

Регрессия на текущем сохранённом снимке проверяет точное равенство всех основных/форумных данных при одинаковом observedAt, включая комментарии, даты и нормализованные события/ТУЗ. Существующие тесты проверяют все личные компоненты и исторические срезы относительно V108. Интерфейсные JS/CSS/HTML не изменены.

Оставшиеся риски:

- Пока нет серверного revision/cursor, изменения с сохранением агрегатов обнаруживаются лишь полной сверкой; максимальная задержка около недели при успешных сверках.
- При неуспешной недельной сверке дата не продвигается: следующие auto-запуски снова пробуют full. При продолжительной недоступности нужно временно выбрать incremental вручную и разобраться с ошибкой до возврата auto; следует наблюдать ошибки и нагрузку, не считать retry бесплатными.
- GitHub может задерживать/пропускать schedule; pending runs не гарантируются. Пять минут — намерение расписания, не SLA.
- До 288 коммитов/деплоев в сутки, стоимость runner/artifact, ограничения Pages и рост history/Git требуют наблюдения. Зависимости кэшируются, браузерные проверки не ставятся в каждый tick. Предел history остаётся прежним 20 MiB: при достижении сбор останавливается для ручного безопасного архивирования.
- Реальный запуск Actions, live API-сбор и production deployment **не проверены**, поскольку не разрешены на этом этапе.

## Безопасное включение после подтверждения

1. Просмотреть ветку и подтвердить слияние в main. До этого расписание production остаётся прежним.
2. После слияния выполнить один manual run mode=incremental, проверить отчёт, request count, неизменность старых комментариев/дат, успешность commit и Pages.
3. Сравнить опубликованные metadata и JSON с коммитом и отображаемыми данными сайта; дождаться нескольких scheduled runs.
4. Полную сверку запустить отдельно вне пика либо дождаться auto-даты. Если API меняется во время чтения, оценить реальный бюджет и не увеличивать скорость без согласования.
5. При проблемах вернуть предыдущий workflow/collector код, сохранив новые data/history и CSV; не откатывать исторические оценки ради отката сборщика.
